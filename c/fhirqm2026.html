medicare shared savings program · a working proposal

Reporting MSSP quality measures from FHIR exports

A plan for completing Medicare CQM reporting for the current performance year using certified FHIR APIs, USCDI data, and AI-assisted abstraction, within existing program rules.

Pathway selection

CMS’s Shared Savings Program scores ACOs on five clinical quality measures, and each ACO chooses among four "collection types" — the defined formats for producing and submitting those measures. Two of the four, eCQMs and the proposed Medicare eCQMs, must be calculated inside certified EHR software, so an independent FHIR pipeline cannot produce them. The other two, MIPS CQMs and Medicare CQMs, use narrative specifications; any data source and computation method is permitted.

This plan uses the Medicare CQM type. Its denominator is limited to Medicare beneficiaries that CMS enumerates, with identifiers, in quarterly lists distributed through the ACO Management System (ACO-MS): the panel is known in advance and patient matching is identifier lookup. Panels run to thousands of patients per participant organization, a volume that per-patient API calls can cover where bulk export is unavailable. Submission is JSON filed through CMS’s Quality Payment Program (QPP) submissions API. An ACO can run this pipeline alongside its existing registry for the first year and choose which output to submit.

A caution about what certification establishes. Certified EHR products are required to offer a standardized FHIR API — the §170.315(g)(10) certification criterion — that exposes patient data as US Core profiles covering the USCDI data classes. Certification is a product test: the vendor’s software demonstrates, against test suites, that it can expose USCDI data through the API. It says nothing about whether a particular provider organization’s live deployment has mapped its actual data into those classes. At runtime, an element a measure needs can be missing from the API response even though it exists in the record — behind an unmapped local code, in a flowsheet that was never connected to the interface, in a scanned document, or only in note text. Experience so far: A1c results and blood pressures generally do arrive as structured US Core Observations; records of colonoscopies done years ago at other facilities, outside mammograms, and the documented follow-up plan required by the depression-screening measure often do not. The design accounts for this with an augmentation path: the same API carries the full text of clinical notes (a USCDI data class), and the pipeline reads those notes to recover elements the structured mapping missed.

The Medicare CQM type has no deemed-pass provisions (the rules that treat the quality standard as met for ACOs completing all-payer digital reporting). The composite score must clear the program’s percentile threshold, or the sharing rate is scaled to the score — a score of 72 yields 72% of the full-rate payment. In a rescoring of the 2024 ACO cohort under current and proposed rules, roughly 25–40% of ACOs clear the threshold on this pathway; in 2022 and 2023, under the prior measurement regime, every ACO passed. Evidence the pipeline recovers raises measured rates, and measured rates determine points and payment.

The same machinery applies to the all-payer MIPS CQM pathway (identical specifications and submission format, larger population). This plan starts with the smaller one.

Measures in scope: glycemic control >9% (Quality ID 001), controlling high blood pressure (236), breast cancer screening (112), colorectal cancer screening (113), and depression screening and follow-up (134), filed under their Medicare CQM identifiers (001SSP and so on).

Mean measured rates for the same measures under three reporting methods, all financially reconciled ACOs, performance year 2024 (CMS public use files). The differences reflect measurement method: sampled manual abstraction (the retired Web Interface) found more qualifying evidence than computation over full populations from structured data. Under the flat benchmarks proposed for Medicare CQMs, ten points of measured rate correspond to one achievement point, about 1.25 points of composite score; in the 2024 cohort, missing the passing standard cost savings-earning ACOs a mean of roughly $4M relative to full-rate payment.

The pipeline

Roster. Ingest the quarterly eligibility list from ACO-MS. Map each listed beneficiary to the participant organizations likely to hold their records, using attribution data and claims feeds.

example 
Eligibility list row:   MBI 1EG4-TE5-MK73 · DOB 1948-03-12 · SMITH, JANET
Claims history shows:   TIN 84-1234567 (Lakeside Primary Care) — 9 E&M visits
                        TIN 84-7654321 (Front Range Cardiology) — 2 visits
Mapped to:              Lakeside (primary record source), Front Range (secondary)

Export. For each participant organization, retrieve the USCDI payload through the certified API surface: the FHIR Bulk Data Access operation (Group/$export) against a managed group of listed beneficiaries where the installed vendor version supports it, per-patient US Core API calls where it does not. Target resources: Condition, Observation (laboratory and vital signs), Procedure, DiagnosticReport, Encounter, and DocumentReference for clinical notes, which the abstraction step reads.

example 
POST /fhir/Group/aco-medicare-cqm-panel/$export
     ?_type=Condition,Observation,Procedure,DiagnosticReport,Encounter,DocumentReference
→ 202 Accepted, poll status URL…
→ complete: observation_1.ndjson (48,112), documentreference_1.ndjson (61,480), …
One NDJSON line: {"resourceType":"Observation","code":{"coding":[{"system":"http://loinc.org",
  "code":"4548-4","display":"Hemoglobin A1c"}]},"valueQuantity":{"value":8.2,"unit":"%"}, …}

Gap triage. For each denominator patient and measure, determine from structured data whether the element is resolved (numerator met, exclusion met, or definitively unmet) or unresolved. Patient 1EG4-TE5-MK73 · measure 113 (colorectal screening):
  structured search → Procedure 45378 (colonoscopy) performed 2019-06-14 → within 10 yr

  → UNRESOLVED → queue 14 clinical notes for abstraction.

Abstraction. Language models read the note corpus for unresolved cases and extract the missing elements. Each finding is emitted as a FHIR resource with a reference to the source note and the supporting text span. CMS may audit submissions; the references support audit response.

example 
From a 2026-02-11 progress note: "…had a screening colonoscopy at Regional Endoscopy
in 2019, normal; repeat in 10 years per report reviewed today."
Emitted resource: Procedure { code: SNOMED 73761001 (colonoscopy),
  performedDateTime: "2019", derivedFrom: DocumentReference/doc-8817,
  extension: { sourceText: "screening colonoscopy at Regional Endoscopy in 2019…" } }

Computation. Measures are computed in TypeScript over the assembled resources. Two implementations are built — one translated from the Clinical Quality Language (CQL) logic published with the corresponding eCQM specifications, one written from CMS’s narrative specifications, which are the governing text for this collection type — and run against a shared test deck of synthetic and hand-constructed edge cases (hospice exclusion, denominator exceptions, the ten-year colonoscopy lookback, the follow-up-plan timing window). Disagreements are resolved against the specification.

example 
CQL (from the CMS130 eCQM):   exists ["Procedure": "Colonoscopy"] C
                                where C.performed ends 10 years or less before
                                end of "Measurement Period"
TypeScript:                    procedures.some(p => inValueSet(p.code, colonoscopyVS)
                                && withinYears(endOf(p.performed), mp.end, 10))

Submission. Emit QPP JSON measurement sets (registry submission type) and file through the QPP Submissions API during the January–March window. Track data completeness per measure against the eligibility list throughout; a measure below 75% completeness is voided regardless of performance.

example 
{ "measurementSets": [{ "submissionMethod": "registry", "programName": "appPlus",
  "measurements": [{ "measureId": "113SSP", "value": {
    "performanceMet": 312, "performanceNotMet": 105,
    "eligiblePopulationExclusion": 12, "eligiblePopulation": 458 } }] }] }
Completeness check: (312+105+12)/458 = 93.7% ≥ 75% ✓

Components worth building in common

Most of this is non-differentiating infrastructure: a per-vendor, per-version inventory of Bulk FHIR and US Core capability, with observed throughput and known defects; group-management and export-orchestration tooling (list-to-group synchronization, retries, incremental re-export via _since, rate limits for the per-patient fallback); gap-triage rules per measure; an abstraction harness with dual-model adjudication, escalation on disagreement, human spot-check sampling with published error rates, and calibration against patients who have both structured and narrative evidence; a profile for abstracted resources carrying provenance; the measure-logic test deck; per-practice completeness dashboards.

Schedule

Submission for the current performance year closes March 31. August: assemble the working group, recruit two or three volunteer ACOs with cooperative participant organizations, complete the endpoint inventory against their EHR installations, ingest the Q3 eligibility list. September–October: export orchestration running; first full-population pulls; abstraction workload sized. November: abstraction at scale; both measure implementations passing the test deck; first end-to-end rates, compared against each ACO’s prior-year reported rates. December: completeness remediation; abstraction spot-review; logic freeze. January: validation against the QPP submissions test environment; reconciliation against the incumbent registry’s parallel output. February–March: submit, with the registry output retained as the fallback.

The parallel run yields paired, same-patient results from two measurement methods. That is calibration data relevant to CMS’s proposed transition to FHIR-based measures, and to comments on the CY2027 proposed rule (due September 14) asking CMS to sponsor dual reporting before any cutover.

Relationship to the 2030 proposal

This plan does not build toward the proposed 2030 architecture — QI-Core-profiled measures executed by certified CQL engines — and does not depend on it. In our view the case for a healthcare-specific DSL and certified execution engine has weakened: AI tools translate measure definitions into ordinary code, and shared test suites verify the results. The pipeline described here uses the API surface that exists, and the data infrastructure it builds is usable under any future measurement approach.
